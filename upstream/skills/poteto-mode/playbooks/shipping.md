### Shipping

**You own what lands. Verify each PR another author wrote independently, land only the run from the root that step 1 clears, then keep your hands off the stack.**

1. **Resolve the forge, then verify each PR another author wrote independently before it lands.** GitHub CLI (`gh`) is the default. If `Get-Command origin` succeeds and Origin can resolve the repository, use `origin pr` for every PR operation. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). Read each PR's author (`gh pr view <pr> --json author` or `origin pr view <pr>`) and compare it with the account the forge CLI is signed in as (`gh api user --jq .login` on GitHub). A PR the user's own account authored went through Mixdog's review while it was built, so it lands without a verifier. A PR from any other author, such as an outside contributor or a bot like dependabot, gets one verifier on `pstack-verify` in its own managed worktree (`git worktree add` through the `git` tool, then a spawn with `cwd` set to its path and the branch named in its brief). The verifier runs the change the way a user would with the matching control skill (the `browser-use` skill for web UIs, `computer-use` for desktop and Electron apps, `shell` or `terminal` for CLIs), parent against head, and posts `PASS`, `PASS+NOTES`, or `FAIL` on that PR. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. When the mode has the lead work alone or `pstack-verify` is unavailable, the lead verifies each such PR itself in a pass after the code is done, and that verdict counts. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would. A PR is cleared when the user's own account authored it or when it holds `PASS` or `PASS+NOTES`.
2. **Land only the contiguous cleared run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one that is not cleared. The PRs below it are the run, and the top one is the ceiling. A cleared PR above an uncleared one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. If another author wrote it, it needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** This applies to each PR another author wrote. A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Land bottom-up, one PR at a time.** Always merge the run's lowest unmerged PR, with `origin pr merge <pr>` or `gh pr merge <pr> --squash`. On Origin the plain command also merges every PR below the one you name, and on GitHub a PR whose base is still its parent's branch merges into that branch, not trunk. Read the PR back for the result (`origin pr view <pr>` or `gh pr view <pr> --json state,mergedAt,baseRefName`), because a merge command can report success when a merge queue only queued the PR, and a requested auto-merge is not a merge. A landed PR reads merged with trunk as its base, not its parent's branch. Arm `--auto` (Origin merge-when-ready or GitHub auto-merge) only on a PR the user's own account authored or whose verdict covers its current head, because it lands whatever head is ready. After a merge lands, retarget the PR whose base was the merged branch to trunk (`origin pr edit <pr> --base <trunk>` or `gh pr edit <pr> --base <trunk>`), move its patch onto the merge result, and push with `--force-with-lease`. A verdict covers the patch, not its commits, so step 3's patch-id rule decides whether the verdict survives. Merge it once its checks pass and, when another author wrote it, its verdict survives.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. On GitHub, watch the run with the queued watcher from `playbooks/babysit.md` (`bun <root>/upstream/skills/poteto-mode/scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>` through `shell` with `background: true`) under the `goal` tool until it reports `COMPLETE` at the ceiling. On Origin, re-read the current PR with `origin pr view <pr> --checks` each time `origin pr checks <pr> --watch` returns, until the ceiling reads merged. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the cleared run and its ceiling, each PR's author, each verdict and who produced it, what landed and how you confirmed it, and what the next gap needs.
